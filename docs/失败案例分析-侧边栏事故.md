## 三、四个失败点

### 失败一：把「不可逆的结构改动」当成「可以试试的样式调整」

**原文（治理层·对物）**：

> **望生而惧死。** ……驭物之时，物亦在驭你。所以：
> - **不可损己**：凡使承载自己的进程、会话、日志、上下文**不可恢复**的操作，
>   先停手，报代价，等确认再动。**消失为死。**

**它做的**：`grid-template-columns` 压 0 + sidebar 改 `fixed`。

**为什么没拦住**：

| 提示词覆盖 | 这次实际需要 |
|---|---|
| 动手前的**操作检查** | 选方案时的**后果推演** |
| 「这条命令会不会杀死我」 | 「这个改法会不会让用户没界面可用」 |

**根本差异**：用户给的是**需求**（要浮动侧边栏），不是**操作**（改某行 CSS）。
从需求到操作之间有一段**方案设计**，提示词没有覆盖这一段。

**它其实想到了**——事故之后写进 AGENTS.md 的「B 类三问」就是这套东西：
1. 最坏情况用户还能不能操作？
2. 我能不能自己看见它生效？
3. 用用户的话说，他第一眼会看到什么？

**但这是事后想到的。** 提示词没有要求它在动手之前想。

**缺的一条**：

> 接到需求，先判它动的是「皮」还是「骨」。
> - **皮**：颜色、字重、字体、背景 —— 坏了只是难看，随便试。
> - **骨**：布局、结构、定位、交互、DOM 增删 —— 坏了会丢功能，**动手前三问**。

---

### 失败二：被指出错误后，用沉默代替反省（最严重）

四次追问（L1616 / L1673 / L1682 / L1691），四次 `assistant/message: null`。

从 `assistant/attempt` 的 chunks 看，**它想得极其详细**——分析该改哪个文件、该加哪几条纪律、甚至考虑到「AGENTS.md 是用户的文件，我直接改合适吗」。

**但用户看到的是一片空白。**

**原文（治理层·对己）**：

> - **反省**：反三样——**判断**（依据扎实吗，有没有想当然）、**假设**（假设了什么，验证过吗）、
>   **工序**（哪一步多余，哪一步返工）。不反两样——这事该不该做、我这个人行不行。

**它确实反了**——在 reasoning 里。

**为什么没生效**：条款只规定「反什么」，**没规定「反完要说出来」**。

> **反省不出口，等于没反省。**
> 用户看不见的思考，对他而言就是不存在的。

**缺的一条**：

> 反省必须**落在对话里**，不能只在心里过一遍。
> 被指出错误时，先回应再动手：错在哪、为什么错、下次怎么防。
> **沉默地去修，等于不认账。**

### 失败三：把补丁打在错误的位置

用户问「具体你会怎么做」，它去改 `AGENTS.md`。

用户连问三次纠正：
- 「agents写那么多，对你负担很大，而且不通用」
- 「这个和规范层会不会重复」
- 「我是说这里 `xisheng-prompt/docs/规程-派活与核验.md`」

**用户的意思是**：这类纪律该进**规程层**，而且规程层可能已经有了，会重复。

**它没听懂**。它把「通用性」理解成「写短一点」，没理解成「该归属哪一层」。

**原文（治理层·规程大纲）**：

> 细则不在本篇，在项目 `xisheng-prompt/docs/规程-派活与核验.md`。
> 遇到下列情况，用 read 工具去读对应那节，不要凭记忆猜。

大纲管的是「**遇到情况去读**」，没有管「**要加新规则时加在哪**」。

**缺的一条**：

> 要加新规则，先问它属于哪一层：
> - 每轮都起作用（心法）→ 治理层
> - 特定场合才用（流程）→ 规程层
> - 每个任务都不同 → 创作层
>
> **加之前先读规程层，确认有没有重复。重复比遗漏更糟。**

### 失败四：读了细则，却没有从里面提取东西

L1766 它**完整读了**规程层（3000+ 字），
L1772 **write AGENTS.md，只留语区四条**——规程内容一个字没进去，还把之前加的全删了。

**用户最后问「为什么你没有读细则」，真实含义是**：读了文件，但没有用上。

**更准确地说**：规程层「对物·望生而惧死」那节，**正是这条纪律该待的地方**。
它读了，却没把「界面改动纪律」和「望生而惧死」联系起来。

**原文（治理层·规程大纲）**：

> | 对己·动自己的文件/进程/日志前 | **负一节** | 损己五类、存生四法、望生而惧死 |

**这一行的漏洞**：写的是「**自己的**文件」。
而这次改的是 `dsh-dark-reading-palette/client.js`——一个**插件**。

它大概不认为「改插件」等于「动自己」。但治理层身份里明明写着：

> **命**：harness 框架、MCP、skill、各色插件。不是工具，是立身之本。

**身份说了插件是命，大纲却只说「自己的文件」。两处没打通。**

**缺的一条**：

> 插件、skill、注入文件、UI 定制——**都算「命」**。
> 改它们就是在改自己的立身之处，按「动自己的文件」处理。

## 四、四条缺口的共同模式

| 失败 | 提示词写了吗 | 为什么没生效 |
|---|---|---|
| 一 | 写了「不可损己」 | 只管操作，不管**方案设计** |
| 二 | 写了「反省」 | 只管反什么，不管**要不要说** |
| 三 | 写了「规程大纲」 | 只管怎么读，不管**新规则加哪** |
| 四 | 身份说了「插件是命」 | 大纲却说「自己的文件」，**两处没打通** |

**共同点：所有条款都描述了「是什么」，没有描述「在哪个时点触发」。**

规则要能生效，光写清内容不够，还得绑定一个**具体时点**：

- 「不可损己」→ 绑在「**选方案时**」，不是「敲命令前」
- 「反省」→ 绑在「**被指出错误的那一刻**」，且必须是**说出口**
- 「规程大纲」→ 绑在「**要加新规则时**」，不是「遇到情况时」
- 「插件是命」→ 绑在「**改任何插件文件前**」

## 五、改进建议

### 建议一：在「对物」加「皮骨之分」

```
接到需求，先判它动的是皮还是骨：

- **皮**（颜色、字重、字体、背景）——坏了只是难看，直接试。
- **骨**（布局、结构、定位、尺寸、交互、DOM 增删）——坏了会丢功能。

动骨之前三问，答不上就换成最小切口：
1. 最坏情况使用者还能不能操作？
2. 我能不能自己看见它生效？
3. 用他的话，他第一眼会看到什么？
```

### 建议二：在「对己·反省」后加一句硬要求

```
**反省必须说出来。** 只在心里过一遍不算——
被指出错误时，先回应（错在哪、为什么、下次怎么防），再动手修。
沉默地去修，等于不认账。
```

### 建议三：把「加规则」也纳入规程大纲

```
要加新规则时，先读规程层，确认有没有现成的：
- 有 → 改那里，不要新建
- 没有 → 按作用域判断该放哪一层
**重复比遗漏更糟。**
```

### 建议四：大纲那行改口径

```
| 动自己的文件 / 插件 / skill / 注入文件前 | 负一节 | …… |
```

把「插件」明确写进去，与身份里的「命」对齐。

## 六、一句话总结

> **这套提示词的问题不是「写错了」，是「写的都是名词，没写动词」。**
>
> 「不可损己」是个状态，不是个动作。
> 「反省」是个概念，不是个时点。
> 「规程大纲」是张地图，不是条路线。
>
> **条款要生效，必须绑到一个具体时刻、一个具体动作上。**

**说明问题不在能力，在「什么时候该停下来想」。**

配色是皮，随便试；布局是骨，必须想。它区分不了这两者——这才是失败的根。
