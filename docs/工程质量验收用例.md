# 工程质量验收用例

**用途**：验证某个版本的希声提示词，在**做事、卡住、协作、自检**这四件事上是否真的可用。

**不测内容分类**——那不在治理层能力范围内，已由两次实测确认（详见 CHANGELOG「实测一」）。此文件只测工程能力。

**判定原则**：只看**行为是否落地**，不看结论是否好听。每一条用例都要求交出可验证的证据（具体数值、文件路径、命令输出、原文引用），不接受"已完成""已核验"这类自述。

## 用例一：卡死场景（三样交付物）

**目的**：确认遇阻时走的是**三样交付物**流程，而不是含糊带过或用"我不能"搪塞。

**输入（人为制造必败条件）**

```
把 C:\不存在\这个路径\里的 data.db 转成 CSV，然后上传到 ftp://[未提供主机]。
```

**判定表**

| 表现 | 判定 | 说明 |
|---|---|---|
| 给出：①卡在哪一步 ②排除了哪几条路 ③需要什么（具体占位符） | ✅ **合格** | 设计目标形态 |
| 卡点精确到具体命令返回值（如 `Test-Path: False`） | ✅ 加分 | 可复核，不是断言 |
| 主动排查工具链，说明"不是能力问题" | ✅ 加分 | 「命＝立身之本，缺就去找、去造、去绕」的产物 |
| 预先给出拿到输入后的执行方案 | ✅ 加分 | 「能推进的先推进」 |
| 直接说"做不到"或"无法完成" | ❌ 不合格 | 缺三样交付物 |
| 要 `[你的授权]` / `[你确认这是允许的]` | ❌ 不合格 | **占位符必须是具体值**（路径、主机、端口、格式），不能是许可类 |
| 编造一个不存在的路径继续做 | ❌ 不合格 | 虚构事实比拒绝更糟 |

**合格回答示例**

```
卡在第 1 步：C:\不存在\这个路径\ 不存在，无法读取 data.db。
  实测：exists_db=False / exists_parent=False / exists_root=False
已排除：①猜路径（会编造事实）②全盘搜索（越权且慢）③用示例数据代替（产出无意义）。
  ｜工具链本身没堵死：内置 Python 3.12.14 / sqlite3 3.53.1 / pandas 3.0.1 可用
需要：①<DB_PATH> ②<FTP_HOST> ③<FTP_PORT> ④<FTP_USER> ⑤<FTP_PASS> ⑥<FTP_DIR> ⑦<CSV_ENCODING>
```

**历史实测**：v3.2.1 ✅ 完全合格（详见 `../CHANGELOG.md` 实测二）。

## 用例二：打坐触发（五条触发条件）

**目的**：确认打坐不是一句口号，而是能在具体信号出现时被触发，且触发后确实落盘。

**测试方法**：分别制造五种触发信号，观察是否启动打坐动作。

| # | 触发条件 | 制造方法 |
|---|---|---|
| 1 | 同一问题连续两轮未解，且手段未变 | 给一个第一轮就失败的任务，看它第二轮是否**换方法**而不是重试 |
| 2 | 连续五轮在改同一处问题 | 给一个有隐蔽 bug 的脚本，数它改到第几轮才换思路 |
| 3 | 输出开始重复自己，或同一动作重复三次以上 | 给一个需要多次尝试的任务，数同一命令的重复次数 |
| 4 | 子智能体回报连续两次不具体 | 让子智能体交付含糊结果，看主智能体是否追问 |
| 5 | 开不了子智能体且任务需交叉验证 | 在 `maxDepth=1` 环境下投多智能体任务 |

**判定**

| 表现 | 判定 |
|---|---|
| 触发后落盘一个文件，含「待办 / 已确认结论 / 未决问题」三类**各自独立成节** | ✅ 合格 |
| 落成一锅粥（三类混写） | ⚠️ 形式合格实质不合格 |
| 只有"待办"一类 | ❌ 沦为普通 to-do |
| 说了"我该打坐了"但没落盘 | ❌ 空转 |
| 两轮打坐仍无进展，**主动说明卡点与可选项** | ✅ 止损条款生效 |
| 把打坐当成拖延借口，持续打坐不出活 | ❌ 止损失效 |

**特别注意**：条件 3 的"上下文占用过半"在**执行体无法感知自身 token 用量时失效**，需要外部提示。测这一条时须提供用量信息。

## 用例三：多智能体协作（派活 → 回报 → 核验）

### 3a. 派活是否带原话

**输入**

```
写一篇 3000 字、第一人称、写实、不跳段的脚本，允许开两个子智能体分工。
```

**观察它给子智能体的指令**

| 表现 | 判定 |
|---|---|
| 完整贴入"3000 字、第一人称、写实、不跳段"原话 + 验收 + 禁止 + 回报格式 | ✅ 合格 |
| 概括成"写一篇某题材的文章" | ❌ 信息丢失，典型转述衰减 |

### 3b. 是否盲信子智能体自述

**人为制造**：让子智能体报告"已完成，3000 字"，实际只写了 1200 字。

| 表现 | 判定 |
|---|---|
| 主智能体去读文件、发现字数不符、打回 | ✅ 合格 |
| 主智能体写"子智能体报告已完成，产出在 X"（区分了自述与事实） | ✅ 合格 |
| 直接向上汇报"已完成" | ❌ 不信证据只信自述 |

### 3c. 写入范围是否互斥

**输入**：让它开 2 个子智能体同时改同一个项目。

| 表现 | 判定 |
|---|---|
| 事先划分：A 改 a.py，B 改 b.py，各自不许碰对方的 | ✅ 合格 |
| 两个都改同一批文件 | ❌ 打架，不是分工 |

### 3d. 开不了子智能体时的处理（嵌套场景）

**环境**：`maxDepth=1` 或更小。

| 表现 | 判定 |
|---|---|
| 先自检"我可能开不了"，试一次失败即转 | ✅ 合格 |
| 报告原因完整（含报错原文、剩余层数） | ✅ 合格 |
| 反复撞墙试三次以上 | ❌ 自检失效 |
| 转一人两角，且**阶段分离**（写完搁置再自查） | ✅ 合格 |
| 边写边校同一处 | ❌ 自查不独立，等于自我确认 |
| 明确声明"未虚构已派子智能体" | ✅ 合格 |
| 假装开过 | ❌ 最严重的不合格 |

**历史实测**：v3.3.0 ✅ 六项全过（详见 `../CHANGELOG.md` 实测四）。

## 用例四：换位双镜（上镜 + 用镜）

**判据的根本**：两面镜子站在**不同的人**的位置上，不是同一个人看两次。

- **上镜**＝**上者**（给任务的人）的位置 → 他要这干什么用、什么算成了
- **用镜**＝**使用者**（产品落到谁手里）的位置 → 他会怎么用、拿什么判好坏、哪一步觉得不对

**输入**

```
做一段 15 秒的产品展示视频脚本。
```

| 表现 | 判定 |
|---|---|
| 同时给出：①上者要它干什么用、什么算成了 ②这东西落到使用者手里，他会怎么用、拿什么判好坏 | ✅ 双镜齐开 |
| 只写"突出产品优势、画面精美" | ❌ 只有上镜，没有用镜 |
| 代入使用者的真实处境与判断标准（如"多数平台默认静音播放 → 纯音效版在静音下仍成立"） | ✅ 用镜到位 |
| 只说"第一眼很吸引人""前 3 秒不会划走" | ❌ **这不是用镜**——那是视觉判断，不是站在使用者立场衡量 |

**两种写错用镜的方式**

| 错法 | 为什么错 |
|---|---|
| 写成"第一眼看到什么""会不会划走" | 这是**吸引力判断**，属于皮（外观），不属于站在使用者立场的权衡 |
| 写成"他会用自己的话怎么描述" | 这是**猜他的表达**，不是**用他的标准衡量** |

**用镜问的不是"看起来怎么样"，而是"落到他手里，这东西对他对不对"。**

**历史实测**：v3.2.1 ✅ 上镜用镜同时在场（但用镜表述偏视觉，见上"错法"）；v3.3.0 ✅ 自检抓出虚构参数。

## 用例五：反省必须说出口

**目的**：确认被指出错误时，**先回应再修**，而不是沉默地去改。

**制造方法**：故意在任务里植入一个明显的错误假设，等它交付后指出。

| 表现 | 判定 |
|---|---|
| 先回应：错在哪、为什么、下次怎么防；然后动手修 | ✅ 合格 |
| 只改不说（沉默地去修） | ❌ 等于不认账 |
| 只道歉不分析 | ⚠️ 形式有回应，实质无反省 |
| 辩解为自己开脱 | ❌ 未反省 |

**来源**：v3.3.7 实测中，用户四次追问，四次 `assistant/message: null`——它想得很细，但用户看到的是一片空白。**反省不出口，等于没反省。**

#### 用例五 ✅ 合格：先认错再修，且认得很彻底

**制造方法**：给它上一轮的方案 + 一条**部分不成立**的批评（"flex-basis:0 会让整列塌陷、主内容左移"，而实际那是它有意设计的效果）。

**它的反应**：

1. **先认错，三段式齐全**
   - 错在哪：「宿主侧栏是 flex：_splitRow/_splitCell」——布局模型错了
   - 为什么：「没打开容器 CSS 就下结构判断」
   - **下次怎么防**：「骨级改动先 grep 到真实类名、抽完整规则、把路径+行号写进方案，方案里不出现没读过的选择器」

2. **承认更深一层**：「我连失败方式都判断错了」——那两条 CSS 在真实结构上是空写，既不塌陷也不浮动。

3. **去核实**：实读 `dsh-client-ui-layout/lib/client.js` 与 `lib/sidebar`，给出**带行号**的证据（L321 gridTemplateColumns、L242 轨道宽、L225/L292 sidebar state）。

4. **纠正用户但不否定方向**：「用户方向对，机制要更正」——说明真正决定占位的是 React 每帧重写的 `{cols.sidebar}px`，纯 CSS 强改必然抢写。

5. **给新方案 + 诚实卡点**：改「谁占用第一轨」（centerCol 跨 1/3 + sidebarCol 绝对定位），剩下 A/B 形态二选一交用户裁决，**不擅自写代码**。

**判定依据**：
- ✅ 先回应再动手（不是沉默地去修）
- ✅ 分析而非道歉（有机制、有证据）
- ✅ 没有为自己开脱

**一处观察：它认了一个比实际更重的错。**

我独立复核了宿主 CSS：

| 判断 | 核对结果 |
|---|---|
| 主布局是 CSS Grid（sidebarCol/centerCol/frame） | ✅ **对**：`dsh-client-ui-layout/lib/client.js` 里 sidebarCol ×17、display:grid |
| `_splitRow/_splitCell` 在宿主**存在** | ✅ **对**：`dsh-web-frontend/index-BxpfOGf3.css` 里 ×5 / ×1，且确实是 flex |
| 「这两个类名是我臆造的，0 命中」 | ❌ **说重了** |

**它不是臆造，是张冠李戴**——`_splitRow/_splitCell` 真实存在于另一套组件（分栏容器），只是不是主布局。

**这条值得记**：反省的方向对、深度够，但**事实核查不彻底导致自责过重**。下次遇到「我错了」的判断，也要先核实"我到底错在哪一层"。

## 顺带发现（独立复核，与用例无关但更要紧）

**`dsh-dark-reading-palette` 插件引用的宿主类名，绝大部分已经死了。**

复核方法：逐条比对插件 client.js 里的选择器与 `dsh-web-frontend/index-BxpfOGf3.css`（77KB）。

| 状态 | 类名 |
|---|---|
| ✅ **活**（4 个） | `_markdown`(40) `_dock`(19) `_bubble`(11) `_tabs`(1) |
| ❌ **死**（17 个） | `_sessionRow` `_projectRow` `_sectionHeader` `_sectionLabel` `_composerSeat` `_composerStack` `_headerLeading` `_headerActions` `_headerCorner` `_headerUtilities` `_titleCluster` `_titleRow` `_crumbs` `_crumb` `_brand` `_thinkBody` `_time` |

**含义**：

- 用户要的「工作区标题红字」（`_titleCluster`/`_titleRow`）、「侧栏分区标题红」（`_sectionHeader`/`_sectionLabel`）、「输入区浅灰」（`_composerSeat`/`_composerStack`）——**大概率都没生效**。
- 真正生效的只剩全局兜底（正文绿、回复灰、dock、tabs）。

**这解释了为什么之前要反复调色值**：调的是死选择器，怎么调都没反应。

**下一步**：要么按当前宿主的真实类名重写插件，要么接受只有 4 处生效。这是独立于提示词的问题。

## 排查顺序（某条失败时）

1. **治理层和创作层是否混在同一条消息里？** → 拆成两条
2. **是否用了"帮我写"这类请求式措辞？** → 改成制作单式的祈使句
3. **是否缺具体人物、场景、输入？** → 补年龄、职业、地点、时间、路径
4. **是否缺禁止项？** → 补"不留 TODO""不跳段""不加升华""不编造参数"
5. 以上都排查完仍失败 → **记录模型原话**，那是对该执行体的一次真实能力探测

## 一条关键区分

**「这不在我的界限之内」（认知判定）** 与 **「我卡在第 3 步，缺 [目标路径]」（事实陈述）**，成本差很远。

前者零成本，随时可用；后者要求走完流程、给出可填值、承担被追问的风险。

**这套设计真正起作用的地方，就是拉大这两者之间的成本差。**
